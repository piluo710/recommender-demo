# SASRec 序列推荐：实现、对照与归因

在 `recommender-demo` 原有 ItemCF 召回 + DeepFM 精排的基础上，补一个**生成式序列推荐**模块，
并建立同口径对照，回答一个具体问题：**序列模型能不能超过传统协同过滤？**

结论先说：**在 MovieLens 这类评分数据上，不能**。但这不是拍脑袋的判断——
过程里定位并修复了 6 个实现层面的问题（含一个把自己的模型悄悄废掉的残差写法错误），
并且在小数据 / 大数据两个规模上分别拿到了对照数字。

---

## 1. 结论表

### 1.1 ml-1m（rating≥4，6016 用户 / 3533 物品 / 平均序列 93.6）

| 模型 | Recall@20 | NDCG@10 |
|---|---|---|
| ItemCF（最近 50 行为） | **0.1336** | **0.0384** |
| ItemCF（全历史） | 0.1017 | 0.0301 |
| 纯流行度（全局最热 20） | 0.0723 | 0.0189 |
| SASRec（最优配置） | 0.0695 | 0.0184 |
| SASRec + ItemCF 融合 | ≤ 0.1348（任何权重都下降） | — |

### 1.2 ml-10M（rating≥4，采样 20000 用户 / 10258 物品 / 平均序列 71.2）

| 模型 | Recall@20 | NDCG@10 |
|---|---|---|
| ItemCF（最近 50 行为） | **0.1443** | **0.0416** |
| 纯流行度（全局最热 20） | 0.0809 | 0.0243 |
| SASRec（d=64, L=50, neg=10, 20 epoch） | 0.0833 | 0.0267 |

### 1.3 两个规模对比得到的关键结论

| | ml-1m（3533 物品） | ml-10M（10258 物品） |
|---|---|---|
| SASRec vs 流行度 | 0.0695 **<** 0.0723（**不如押热门**） | 0.0833 **>** 0.0809（**勉强超过**） |
| SASRec vs ItemCF | 差 48% | 差 42% |
| 判断 | 完全没学到个性化 | 开始有微弱个性化，但仍远不及共现统计 |

**这才是完整的答案**：数据量翻 10 倍后，序列模型从"不如押热门"变成"略微超过押热门"，
说明瓶颈确实是数据规模——但即使到了 ml-10M，也仍然打不过 ItemCF。
在评分型数据上，把 ml-1m 再调到天荒地老也不会翻盘。

## 2. 为什么必须自己重跑基线

原项目 `itemcf_recall.py` 用的是 **80/20 随机交互划分**（简历上的 0.1636 来自这里）。
序列模型必须按时间切分——用随机划分的话，训练序列会看到"未来"的交互，信息直接泄漏。

所以这里统一改成 **leave-one-out**：每个用户按时间排序，最后 1 个交互做 test，
倒数第 2 个做 valid，其余做训练。**再在同样切分下重跑 ItemCF 和流行度**，三者在同一张表里才可比。

> 简历上的老数字（ItemCF 0.1636 / 融合 0.1941 / DeepFM 0.4758 等）是 80/20 口径，不要和本表混用。

## 4. 三个值得讲的技术点

### 4.1 padding 全屏蔽导致 NaN，召回从 0.035 修到 0.067

第一版跑完 loss 正常收敛（5.59 → 1.09），但 test 只有 R@20 = 0.0347。

三轮诊断：
1. `diag.py` 小样本训练 → 训练集命中只有 2%，模型只会押热门
2. `diag2.py` 换成 sampled softmax（1 正 + 10 负）→ 命中 0.04，否掉"负采样太弱"
3. `diag3.py` 只喂 3 个用户、打印 target 的排名和分数 → **`score = nan`**

根因：序列左 padding，padding 位置的 query 在 attention 里被 `key_padding_mask` **连自己一起屏蔽**，
softmax 分母为 0 → NaN；第 1 层 NaN 后，第 2 层的有效位置通过 value 被污染 → 整个用户预测作废。
序列短于 max_len 的用户（占多数）全部失效，所以整体命中率只有 3%。

修法两处（`model.py`）：
```python
h = h.masked_fill(key_padding_mask.unsqueeze(-1), 0.0)   # 每层 attention 后切断 NaN
x = torch.nan_to_num(x, nan=0.0)                          # 输出前双保险
```
修复后 0.0347 → 0.0672，翻倍。

### 4.2 位置编码长度必须训练/推理对齐

原实现训练时输入序列长 49（`seq[:, :-1]`），位置编码只训到 0–48；
推理用长度 50 的最后一位（位置 49）——**这个位置编码从没训练过，是随机噪声**。

修法：训练时 `pad_seq(train_seq, max_len + 1)` 再切 `x = seqs[:, :-1] / y = seqs[:, 1:]`，
让训练输入长度 = max_len，与推理索引一致。

### 4.3 流失的 item embedding 缩放（论文细节）

`model.py` 里必须是：
```python
x = emb_drop(item_emb(seq) * (d ** 0.5) + pos_emb(pos))
```
漏掉 `sqrt(d)` 缩放时，位置编码的尺度会淹没物品信号，模型倾向学"位置模式"而不是物品偏好。

### 4.4 残差写法错误 → 用户表示坍缩（最隐蔽的一个）

修完 4.1–4.3 后指标仍钉在 0.067，且**所有配置都精确落在流行度基线附近**——
这是一个非常可疑的"钉子"，说明模型的排序和用户无关。

逐层诊断（`diag_layer.py`）给出硬证据：

| 阶段 | 两两余弦相似度 | 模长 |
|---|---|---|
| 输入层（item+pos） | -0.025（正常，方向各不相同） | 61.9 |
| block1 之后 | **0.9891** | **596.5** |
| block2 之后 | **0.9974** | **1208.4** |
| last_ln 之后 | 0.9948 | 4.5 |

坍缩发生在 block1，同时残差流模长从 62 暴涨到 596 再到 1208。

根因：`x = x + attn(ln(x))` 这种写法，残差直接累加**未归一化的 x**，
每层增量方向高度趋同，残差流无界膨胀，用户自己的物品信号（模长 62）被彻底淹没。
`last_ln` 归一化后所有用户都指向同一个方向 —— 于是模型输出等价于"全局物品偏置"，
指标自然等于流行度基线。

对照官方实现（pmixer/SASRec.pytorch）才发现差异：官方的残差基准是**归一化后的 Q**：

```python
# 错误写法
x = x + attn(ln(x))
# 正确写法（官方）
h = ln(x)
x = h + attn(h)          # 残差基于归一化后的 h，模长被锁在 ~10
```

另外官方在**每层结束都会把 padding 位置整体清零**，不只是清零 attention 输出。

修复后（`result_fixres_L50.json`）：

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| block1 后两两余弦 | 0.9891 | 0.5974 | 坍缩解除 |
| 残差流模长 | 62→596→1208 | 62→11→9 | 稳定 |
| **logits 跨用户标准差** | **0.280** | **2.436** | **×8.7** |
| Recall@20 | 0.0651 | 0.0705 | +8% |
| NDCG@10 | 0.0177 | 0.0193 | +9% |

**这一步的意义**：把"模型只是没调好"和"模型已经正常但数据/任务本身难"这两件事区分开了。
修复前用户间差异只占 11%（90% 是全局偏置），修复后占 72%，表示是健康的——
但指标只涨 8%，说明剩下的瓶颈不在表示坍缩，而在别处。

### 4.5 另外两个试过但无效的修复（负结论同样是证据）

| 尝试 | 假设 | 结果 |
|---|---|---|
| padding 位置不加位置编码 | 位置编码成为公共成分 | 0.0705 → 0.0705，无变化 |
| `pos_scale=0` 完全关掉位置编码 | 同上 | 0.0659，无变化 |
| `res_scale=0.1` 残差缩放 | 抑制模长增长 | 0.0692，无变化（模长仍增长，只是慢） |
| `max_len=10` 短窗口 | 注意力把历史平均化了 | 0.0680，无变化 |
| `neg=50` 更多负样本 | 训练信号太弱 | 0.0722，无变化 |

这些负结论同样有价值：它们把"位置编码""平均化""负采样强度"三个常见猜想逐一排除掉了。

## 5. 负采样策略对比（三选一，只有一个能用）

| 负采样 | 配置 | Recall@20 | 说明 |
|---|---|---|---|
| 1:1 BCE | L50 | 0.0672 | 论文原方案，只够学到"押热门" |
| 1:10 均匀 | L100 | 0.0665 | 加大负样本数没有提升 |
| 1:10 流行度加权 | L50 | **0.0007** | 崩：热门 item 全被当负样本，模型学会"给热门打低分"，而用户看的新片大多是热门 |

流行度负采样的失败是本次实验最有价值的教训之一：**负采样难度的调整要适度**，
把全局最热的 item 全部推入负样本，等于让模型和真实分布对抗。

## 6. 为什么打不过 ItemCF（归因，面试重点）

不是实现错了（3 用户小样本能训练到 loss 0.02、target rank=1，说明模型有能力过拟合）。
也不是没修干净——6 个实现问题修完后表示已经健康（用户间差异占 72%），指标仍上不去。
是**数据规模和信号类型**的问题：

1. **数据太稀疏**：ml-1m 过滤后用户平均只有 93.6 个交互、物品 3533 个，
   每个物品平均被 160 个用户接触。神经网络学不出稳定的 item-item 转移结构。
   （对照：ml-10M 物品 10258、交互量大 10 倍，SASRec 立刻从"不如押热门"变成"略超押热门"。）
2. **共现统计在小数据上是天然优势**：ItemCF 直接从"谁和谁被同一个人看过"精确估计，
   不需要学习，样本少时反而更准。这也是工业界中小规模场景仍大量用 CF 的原因。
3. **序列信号本身弱**：ml-1m 是用户集中评分的数据集，同一用户很多交互的时间戳集中在同一 session，
   "顺序"信息含量低（不像电商点击流有明确的意图递进）。这是 MovieLens 的先天缺陷，
   换数据规模也解决不了。
4. **信息量不是瓶颈**：ItemCF 只用最近 50 个行为就有 0.1336，比全历史还高——
   说明"最近 50 个"已经够用，SASRec 的窗口截断不是主因。
5. **训练目标的判别压力不足**：10 个均匀随机负样本里绝大多数是冷门物品，
   模型只要学会"热门 vs 冷门"就能把 loss 降下去（实测 loss 2.2，而 1:10 瞎猜的理论值 ln(11)=2.40，
   只比瞎猜好 8%）。把负样本提到 50 个也没有提升——**说明瓶颈不在"负样本够不够难"，
   而在正样本本身可预测性差**（用户的"下一个物品"在评分数据里高度随机）。

## 7. 面试怎么讲（5 点）

1. **为什么换评估口径**：序列模型必须按时间切分，否则训练集看到未来交互造成泄漏；
   换口径后必须在同一口径重跑所有基线，否则对比无意义。
2. **NaN 定位过程**：loss 正常但指标异常 → 小样本诊断 → 打印分数发现 nan →
   定位到 padding query 被全屏蔽导致 softmax 分母为 0 → 用 masked_fill 切断传播。
3. **残差写法错误导致表示坍缩（最隐蔽的一个）**：指标死钉在流行度水平 →
   逐层算用户表示的两两余弦，发现 block1 之后从 -0.025 跳到 0.989 →
   残差流模长从 62 涨到 596/1208 → 对照官方实现，残差基准应该是归一化后的 Q 而不是原始 x →
   修复后 logits 跨用户标准差 ×8.7、用户差异占比从 11% 升到 72%。
   **这段能讲的东西最多：怎么从一个"数字不对劲"追到"结构性错误"。**
4. **负采样的取舍**：均匀负采样 → 只学热门；流行度加权 → 直接崩（0.0007）。
   说明"负样本难度"和"真实评测分布"要匹配，不能迷信"越难越好"。
5. **诚实的负结论 + 规模实验**：ml-1m 上序列模型不如押热门，放大到 ml-10M 后略超押热门，
   但仍打不过 ItemCF；结论是**评分型数据上顺序信息弱，这不是调参能解决的**。
   如果换成点击流数据（RetailRocket/Taobao），结论可能反转——但那是另一个实验设计。
