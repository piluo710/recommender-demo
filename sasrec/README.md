# SASRec 序列推荐：实现、对照与归因

在 `recommender-demo` 原有 ItemCF 召回 + DeepFM 精排的基础上，补一个**生成式序列推荐**模块，
并建立同口径对照，回答一个具体问题：**序列模型能不能超过传统协同过滤？**

结论先说：**能，而且不是靠调参，是靠修掉一个把训练废掉的输出层 bug**。
过程中一共定位并修复 **7 个模型实现问题 + 5 个评估链路问题**，其中 3 个模型问题（NaN、残差坍缩、输出层尺度）
每一个单独存在时都会让模型退化成"押热门"。修完最后一个，ml-1m 全评分口径从 **0.0730 → 0.1871**。

## 2. 为什么必须自己重跑基线

原项目 `itemcf_recall.py` 用的是 **80/20 随机交互划分**（简历上的 0.1636 来自这里）。
序列模型必须按时间切分——用随机划分的话，训练序列会看到"未来"的交互，信息直接泄漏。

所以这里统一改成 **leave-one-out**：每个用户按时间排序，最后 1 个交互做 test，
倒数第 2 个做 valid，其余做训练。**再在同样切分下重跑 ItemCF 和流行度**，三者在同一张表里才可比。

> 简历上的老数字（ItemCF 0.1636 / 融合 0.1941 / DeepFM 0.4758 等）是 80/20 口径，不要和本表混用。

## 4. 值得讲的技术点（7 个，按发现顺序）

### 4.1 padding 全屏蔽导致 NaN，召回从 0.035 修到 0.067

第一版跑完 loss 正常收敛（5.59 → 1.09），但 test 只有 R@20 = 0.0347。

三轮诊断：
1. `diag.py` 小样本训练 → 训练集命中只有 2%，模型只会押热门
2. `diag2.py` 换成 sampled softmax（1 正 + 10 负）→ 命中 0.04，否掉"负采样太弱"
3. `diag3.py` 只喂 3 个用户、打印 target 的排名和分数 → **`score = nan`**

根因：序列左 padding，padding 位置的 query 在 attention 里被 `key_padding_mask` **连自己一起屏蔽**，
softmax 分母为 0 → NaN；第 1 层 NaN 后，第 2 层的有效位置通过 value 被污染 → 整个用户预测作废。
序列短于 max_len 的用户（占多数）全部失效，所以整体命中率只有 3%。

修法：每层 attention 后 `masked_fill` 清零，输出前 `nan_to_num` 双保险。修复后 0.0347 → 0.0672。

### 4.2 位置编码长度必须训练/推理对齐

原实现训练时输入序列长 49（`seq[:, :-1]`），位置编码只训到 0–48；
推理用长度 50 的最后一位（位置 49）——**这个位置编码从没训练过，是随机噪声**。

修法：训练时 `pad_seq(train_seq, max_len + 1)` 再切 `x = seqs[:, :-1] / y = seqs[:, 1:]`。

### 4.3 流失的 item embedding 缩放（论文细节）

```python
x = emb_drop(item_emb(seq) * (d ** 0.5) + pos_emb(pos))
```
漏掉 `sqrt(d)` 缩放时，位置编码的尺度会淹没物品信号。

### 4.4 残差写法错误 → 用户表示坍缩

修完 4.1–4.3 后指标仍钉在 0.067，且**所有配置都精确落在流行度基线附近**——
这个"钉子"说明模型的排序和用户无关。

逐层诊断（`diag_layer.py`）：

| 阶段 | 两两余弦 | 模长 |
|---|---|---|
| 输入层 | -0.025（正常） | 61.9 |
| block1 之后 | **0.9891** | **596.5** |
| block2 之后 | **0.9974** | **1208.4** |

根因：`x = x + attn(ln(x))` 的残差直接累加**未归一化的 x**，逐层无界膨胀，用户信号被淹没。

```python
# 原写法：残差累加原始 x，尺度没有任何约束
x = x + attn(ln(x))

# 现在的写法：残差基准 = ln(x)，残差流被锁在 ~sqrt(d) 量级
h = ln1(x)
x = h + drop(attn(h)) * res_scale
x = x.masked_fill(key_padding_mask.unsqueeze(-1), 0.0)   # 每层结尾整体清零 padding
h = ln2(x)
x = x + drop(ffn(h)) * res_scale
```

> **诚实说明**：标准 pre-LN 的写法是 `x = x + attn(ln(x))`（残差基于原始 x），
> 我们这一条是**偏离标准写法的自定义改造**，不是官方实现。它的作用是把残差流模长
> 锁在 LayerNorm 的输出尺度（约 sqrt(64)=8）上。实测确实解除了坍缩，
> 但没有逐行比对过官方源码（`web_fetch` 取 raw.githubusercontent.com 失败），
> 所以这里不声称"官方就是这么写的"。

修复后 logits 跨用户标准差 ×8.7（用户差异从 11% 升到 72%），但指标只 0.0651 → 0.0705。

### 4.5 两个危险默认值（会让任何人踩坑）

| 参数 | 旧默认 | 后果 | 改为 |
|---|---|---|---|
| `res_scale` | 0.1 | 残差只剩 10%，模型近乎只做一次 LayerNorm | 1.0 |
| `neg_mode` | pop | 按流行度采负样本，实测崩到 0.0007 | uniform |

含义：早前 `L10` / `nopos` / `fix_posmask` / `resscale01` 四组都是在 `res_scale=0.1` 的退化配置下跑的，
**它们的"无效"结论不可信**。

### 4.6 输出层点积尺度 → softmax 温度过低（最后一个，也是最关键的一个）

修完 4.1–4.5，指标还是 0.070。继续查"模型到底在推荐什么"（`diag_what.py`）：

| 诊断项 | 修复前 | 修复后 |
|---|---|---|
| 30 个用户两两 top20 平均重合 | **8.45/20（42%）** | **1.13/20（5.6%）** |
| top20 与全局最热 top20 重合 | **9.27/20（46%）** | **2.10/20（10.5%）** |
| item_emb 模长 vs 流行度 Spearman | -0.044（模长不是原因） | 0.004 |
| item_emb 与"用户表示均值方向"余弦 vs 流行度 | **0.957** | 0.932 |

前两项说明：模型给所有用户推的东西有 46% 是全局最热——**它就是个流行度模型**。
第四项说明机制：热门 item 被大量用户当正样本，embedding 被拉向"用户表示的公共方向"，
冷门 item 很少被采样、方向基本没动。输出层点积时公共方向的分量说了算。

为什么只学得到热度？`diag_fpmc.py`（去掉 attention、只留 item embedding）给出反证：

| 模型 | Recall@20 | 训练 loss |
|---|---|---|
| 纯 item embedding（无 attention） | **0.0063 ≈ 随机** | 卡在 **13.5** 不动 |

`ln(11) = 2.4` 是"11 个候选里瞎猜"的理论值，loss 13.5 说明模型在主动犯错。
根因：`x @ item_emb.T` 的点积尺度达 40–60，softmax 温度极低、接近 one-hot，
梯度只作用在分数最高的那几个物品上，其余 3700 个物品几乎不动 → 学不出物品关联。

修法：输出层改余弦相似度 + 固定温度。

```python
x = F.normalize(self.encode(seq), dim=-1)
w = F.normalize(self.item_emb.weight, dim=-1)
return (x @ w.T) * 20.0        # logit_scale = 20
```

修复后（ml-1m 全评分，70 epoch）：

| 指标 | 点积输出层 | 余弦输出层 | 变化 |
|---|---|---|---|
| 训练 loss（末轮） | 卡在 13.5（前 30 轮 12→13） | 3.86 → **1.07** | 真正在学 |
| valid Recall@20 | 0.073 | **0.196** | ×2.7 |
| **test Recall@20** | **0.0730** | **0.1871** | **×2.56** |
| test NDCG@10 | 0.0210 | **0.0607** | ×2.89 |
| 用户两两 top20 重合 | 8.45/20 | 1.13/20 | 千人一面消失 |
| 与全局最热重合 | 9.27/20 | 2.10/20 | 不再押热门 |

**这一条是整个项目最有价值的发现**：前面 6 个 bug 修完后指标纹丝不动，
真正卡住模型的是"输出层尺度"这种看起来最不像 bug 的地方——
它不会报错、不会 NaN、loss 也在缓慢下降，只是学得极慢，慢到看起来像"数据不行"。

### 4.7 试过但无效的修复（负结论同样是证据）

| 尝试 | 假设 | 结果 |
|---|---|---|
| `pos_scale=0` 完全关掉位置编码 | 位置编码是公共成分 | 0.0730 → 0.0717，无变化 |
| `res_scale=0.1` 残差缩放 | 抑制模长增长 | 0.0692（且该配置本身是退化的） |
| `max_len=10` 短窗口 | 注意力把历史平均化了 | 0.0680 |
| `neg=50` 更多负样本 | 训练信号太弱 | 0.0722 |

位置编码这条用 `pos_scale=0` 在**正确配置**（`res_scale=1.0`）下重测过：0.0717，确实不是原因。

### 4.8 第二轮自查：五个"不报错但结论已经错了"的问题

上面 7 个是**模型自己错了**。第二轮把评估链路和诊断脚本也过了一遍，又找出 5 个同类气质的坑：

| # | 问题 | 为什么危险 | 修法 |
|---|---|---|---|
| 1 | `SASRec.__init__` 没有 `norm_out` 属性，训练时靠外部动态赋值；权重只存 `state_dict` | 任何人加载 `best.pt` 都默认走点积分支，拿到**看起来合理、其实完全错**的分数 | `__init__` 里给默认值；训练结束把推理配置写进 `best_meta.json` |
| 2 | 诊断脚本加载权重后没有还原推理模式 | `diag_what.py` 用点积测余弦版权重，报出的重合率是错的（真实 1.13 被报成 1.38） | 从 meta 读，缺失时打印明确警告，不默认猜 |
| 3 | 基线排除集只排 `train`，而 SASRec 排 `train ∪ {valid}` | **两边评测口径不对等**：ItemCF 的 valid item 白占一个 top20 名额，对照表的差值不可信 | 统一成 `train ∪ {valid}` 并重跑基线 |
| 4 | 基线结果文件名不带数据集/口径 | ml-10M 覆盖 ml-1m、rating≥4 覆盖全评分，事后根本无法凭文件名判断数字属于哪个口径 | 文件名带 `dataset` 和 `min_rating` |
| 5 | `diag_fpmc.py` 的 `valid_pairs` 目标写成了 `test` | 早停实际上是在**测试集上选 epoch**，指标虚高 | 改成 `(train[u], valid[u])` |

**这五个的共同点：都不会抛异常。** 跑得通、loss 在降、数字看着也正常，但结论已经被悄悄污染了。
所以自查不能只看"能不能跑起来"——要拿**已知必须成立的约束**去反查，
比如"两个模型的排除集必须完全相同"，一条就够把第 3 条揪出来。

另外给 `encode()` 加了输入长度断言：`pos_emb` 只有 `max_len` 行，
长度超了以前是静默越界，现在直接抛 `ValueError`，防止"训练 49、推理 50"那类问题重演。

**口径修正后的对照表**（ItemCF 数字比修正前略高，因为排除了 valid）：

| 口径 | SASRec | ItemCF | 优势 |
|---|---|---|---|
| ml-1m 全评分 | 0.1871 | 0.1611（原 0.1581） | **+16.1%** |
| ml-1m rating≥4 | 0.1544 | 0.1348（原 0.1336） | **+14.5%** |
| ml-10M rating≥4 | 0.1576 | 0.1457（原 0.1443） | **+8.2%** |

差距比修正前略小，但结论不变：**三个口径都稳定超过 ItemCF**。

### 4.9 第三轮自查：评估数字独立复算 + 融合实验用正确分数重做

第二轮修完评估链路后，还有一个问题悬着：**train.py 的 `evaluate` 本身就是被怀疑对象**，
用同一个函数再跑一遍证明不了任何事（同一个 bug 会稳定给出同一个错数）。
所以本轮新写 `verify_metric.py`，用**三条互不依赖的实现路径**重算：
numpy `argsort` 全排序（不是 `topk`）、全排序后按集合过滤（不是 `-1e9` 掩码）、
显式位置循环算 NDCG、batch=1 逐用户。

全量 6040 用户复算结果：**Recall@20 = 0.1871 / NDCG@10 = 0.0607，和 train.py 逐字节一致**；
且"掩码 top20"与"集合过滤 top20"**逐用户不一致数 = 0**。0.1871 这个数可信。

同一轮还清了三个"结构参数没进 meta"的定时炸弹：

| # | 问题 | 修法 |
|---|---|---|
| 1 | `model.py` 注释谎称"官方实现：seqs = Q + mha_outputs"，与 §4.4 的诚实说明自相矛盾 | 注释改为"自定义改造，偏离标准 pre-LN，不声称与官方一致" |
| 2 | `logit_scale` 不在 `best_meta.json` 里，一旦调温度，加载方会静默用错 | `save_ckpt` 写入 meta；已有 3 个 meta 补 `logit_scale: 20.0` |
| 3 | `diag_what.py` 用命令行默认值重建结构（`pos_scale`/`res_scale` 根本没传） | 新增 `build_from_meta()`，全部结构参数从 meta 还原；所有脚本统一走该入口 |

**融合实验重做（推翻旧结论）**：`fuse_sasrec.py` 原来直接 `SASRec(...)` 构造、
`model(seqs)` 不传 `norm_out`——融合用的是**旧点积分数**，"融合无增益（w=0 最高）"
这个结论是错的。改用 `build_from_meta` + 余弦分数重跑（全评分口径，6040 用户）：

| w(SASRec) | Recall@20 | NDCG@10 |
|---|---|---|
| 0.0（纯 ItemCF） | 0.1611 | 0.0459 |
| 0.3 | 0.1829 | 0.0529 |
| 0.5 | 0.1990 | 0.0598 |
| **0.7（最优）** | **0.2081** | **0.0660** |
| 1.0（纯 SASRec） | 0.1871 | 0.0607 |

**两路明显互补**：融合比纯 ItemCF 高 29.2%、比纯 SASRec 还高 11.2%。
这也说明点积分数的旧结论（"SASRec 没增量信息"）是错的——是分数本身不可用。

另外把所有诊断脚本的 `min_rating` 默认值改成**跟随 `best_meta.json`**（新增
`dataset.default_min_rating_from_meta()`）：之前 `diag_layer`/`diag_repr`/`diag_modulus`/
`diag_collapse2` 默认 4，遇到全评分权重直接 size mismatch 崩溃，或者更糟——物品数
恰好相同时静默算错。

## 5. 负采样策略对比

| 负采样 | 配置 | Recall@20 | 说明 |
|---|---|---|---|
| 1:10 均匀 | L50，点积输出层 | 0.0665–0.0722 | 现用方案 |
| 1:1 BCE | L50，点积输出层 | 0.0672 | 论文原方案 |
| 1:10 流行度加权 | L50，点积输出层 | **0.0007** | 崩：热门 item 全被当负样本，模型学会"给热门打低分" |

> 该表数字全部来自点积输出层版本。余弦输出层下未重做负采样对比。

流行度负采样的失败是重要教训：**负采样难度的调整要适度**，
把全局最热的 item 全部推入负样本，等于让模型和真实分布对抗。

## 6. 归因：0.073 那组数字到底错在哪（面试重点）

一句话：**不是数据不行，是训练根本没学动，只是它不报错。**

证据链，按发现顺序：

1. **先排除"实现有硬错"**：NaN、位置编码、sqrt(d)、残差坍缩全修完 → 0.0705，几乎不动。
2. **再排除"表示没信息"**：`diag_layer.py` 显示用户表示两两余弦已从 0.995 降到 0.60，
   logits 跨用户标准差 ×8.7，表示是健康的。
3. **再看"推荐了什么"**：`diag_what.py` → top20 与全局最热重合 46%，用户之间重合 42%。
4. **最后做隔离实验**：`diag_fpmc.py` 去掉 attention 只留 item embedding → 0.0063、loss 卡 13.5。
   说明连最基础的"物品共现"都学不出来 → 问题在训练目标/输出层，不在序列建模。
5. **定位到尺度**：点积 40–60 → softmax 近 one-hot → 梯度只落在极少数物品上 → 改余弦 + 温度 → 0.187。

值得讲的是这个顺序：**每一步都用"能证伪的指标"否掉一个假设**，
而不是靠调参碰运气。这也是为什么最后翻盘不是偶然。

## 7. 面试怎么讲（5 点）

1. **为什么换评估口径**：序列模型必须按时间切分，否则训练集看到未来交互造成泄漏；
   换口径后必须在同一口径重跑所有基线，否则对比无意义。
2. **三个会伪装成"数据不行"的 bug**：padding 掩码致 NaN、残差基准错致表示坍缩、
   输出层尺度致 softmax 温度过低。它们的共同点是**不报错、loss 还在缓慢下降**，
   只能靠"指标死钉在某个基线附近"这种异常去反查。
3. **怎么定位的**：逐层算用户表示的两两余弦（发现 0.995 坍缩）→ 算 top20 与热门的重合度
   （发现 46% 在押热门）→ 去掉 attention 做隔离实验（发现连共现都学不出来）→
   锁定输出层尺度。**每一步都是一个能证伪的指标。**
4. **负采样的取舍**：均匀负采样 → 只学热门；流行度加权 → 直接崩（0.0007）。
   说明"负样本难度"和"真实评测分布"要匹配。
5. **最终结果**：ml-1m 两个口径都超过 ItemCF（全评分 0.1871 vs 0.1611，rating≥4 0.1544 vs 0.1348），
   且用户两两 top20 重复率从 42% 降到 5.6%、与全局最热重复率从 46% 降到 10.5%——
   **能证明它学到的是个性化，不是押热门。**

## 8. 简历可以怎么写

推荐（诚实 + 体现排查能力 + 有量化）：

> **序列推荐补做（SASRec）**：自建 leave-one-out 评估体系与同口径基线，独立实现 SASRec；
> 定位并修复 7 个模型实现问题 + 5 个评估链路问题（含 padding 掩码致全用户 NaN、残差基准错致用户表示坍缩、
> 输出层点积尺度致 softmax 温度过低），ml-1m 全评分口径 Recall@20 从 0.073 提升到 0.187，
> 超过同口径 ItemCF 16.1%；与 ItemCF 加权融合达 **0.208（+29.2%）**，验证两路互补；
> 并通过 top20 重合率（42%→5.6%）验证个性化确实生效。评估数字用独立实现路径复算核对。
